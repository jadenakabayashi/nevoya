The thesis

One root cause, three unlocks

Three separate objectives on the roadmap all trace back to the same root cause: our operational data isn't true or live. Fix that, and three things unlock at once.

  • Planning/Tracking UI becomes a revenue feature — not just a facelift. It catches legitimate detention-chargeable dwell, improves loaded-miles utilization, and protects value we already have (Amazon).
  • California can confidently migrate to Apollo — though we're likely going for it regardless.
  • We can start capturing what GMA's ZETc program needs.
    • Leads with data-trust work — the dependency under the planning/tracking tool, and already has work in the hopper06 / 15

    Option 1 · the payoff

    Planning Tool Redesign — the consumer, not a parallel project

    Today the planning page builds a schedule from data that's usually stale by the time a dispatcher looks at it. This redesign isn't a nicer UI in parallel — it's the thing that makes items 1–5 worth doing in the first place, by surfacing all of it inline.

  • #1 — the corrected truck/driver assignment, instead of a schedule showing the wrong driver
  • #2 — a dwell-exceeded flag with time-below-target the moment it fires, instead of a dispatcher happening to notice
  • #3 — a load-level ETA that already accounts for the prior leg's delay, instead of a naive per-shift number
  • #4 — a one-click way to log what happened and what a dispatcher did about it, instead of that response leaking into Slack or a spreadsheet
  • #5 — Shift Doctor's diagnosis surfaced automatically, instead of someone having to ask for it
    • Planning viability needs scoring — but it's what gets users to love Apollo, capture the data, and grow revenue08 / 15

    Checkpoint

    Does this make the ETA correct? Not completely.

    Dwell detection, delay attribution, and Shift Doctor v2 are all "give humans better tools to investigate and surface when something's wrong" — not "make the number so good nobody needs to look twice."

    Recommendation

    Ship two-click dispatch and display the ETA first — then observe whether that alone fixes trust before investing in any reconciliation or surfacing layer. Three of the five items above would support that layer if it's still needed.

    Also worth building: a relay swap-point evaluation tool that scores existing swap-point options — decision support for a human or an agent. It's a named dependency for Re-dispatch Agent, and gives Delay Attribution's relay_handoff code a reason to split into a sub-code for "wrong swap point chosen" vs. generic handoff overhead.

    Option 2

    Driver shift constraints and Driver shift redesign first

    Driver shift constraints is the highest-leverage single item on the board: it's a dependency for both the Re-dispatch Agent and the Planning Agent — two of the four decision agents.

  • Best leverage-per-effort. No other idea unlocks two of the four named decision agents at once. Load weights, charging sessions, and SOC data are each needed by only one agent or tool.
  • Would better support California moving to Apollo.
  • Doesn't depend on unblocking anything first.
    • Honest callout

    Won't move revenue or agentify planning the way stop-duration quantiles or resuming dwell detection will — and it needs real design work.

    Foundational-data items

    For the Planning Agent, and agentifying planning more broadly:

  • Driver shifts data model migration
  • Load weights from rate confirmation
  • Charging sessions as first-class data

    Option 3

    Mature the optimizer that's already running

    Already past "rung 1," really mid-rung 2 on the autonomy ladder: the system proposes via CP-SAT, a human stays fully in the loop reviewing before trusting it. The running optimizer already handles unassigned-leg penalties, deadhead, idle time, appointment windows, HOS, shift windows, no-overlap, and return-to-base constraints.

    Rung 1
    Manual
    Rung 2 (mid)
    CP-SAT proposes, human reviews
    Rung 3
    Less oversight
    Rung 4
    Automated planning

    The optimizer's own doc calls out its biggest blind spot: stop duration is fed into CP-SAT as a single deterministic number today — "we are already making a risk decision, but we make it implicitly." A 4-phase fix is already scoped in Notion:

    Phase 1Quantile model
    Phase 2Risk-aware reservation policy
    Phase 3Pooled slack
    Phase 4Route-level probability

    The quantile model needs real historical actual-vs-planned stop-duration data to calibrate against — resuming Late/Dwell Detection (Option 1, #2) provides exactly that feed. Driver shift constraints still matters here too: the optimizer models HOS and shift start/end, but nothing about driver availability or preference.

    An older "Greedy Optimizer" doc (Feb 2025) already covers driver/truck/load matching, EV range, and charging-insertion feasibility13 / 15
    Option 3 · what the optimizer is waiting on

    Data work that supports the optimizer

    SOC / range reliability
    The optimizer's feasibility check — current_SOC − energy needed ≥ min_safe_SOC. Blocked by the odometer cache; Rohan's Kafka work will provide trustworthy data.
    Dynamic charger availability integration
    The optimizer assumes a charger is reachable and available today — there's no live feed of occupancy or outages yet.
    Trailer Pool Management
    The optimizer has an empty_trailer_pickup stop type and assumes the trailer will be there — this makes it a precondition for one of the optimizer's own stop types, not just a dispatcher UI tool.
    Appointment / time-window data integrity
    The optimizer's hard time-window constraint is only as good as whether "planned time" and the real appointment line up.
    Location-naming consistency
    The optimizer matches on Location records — duplicate or inconsistent naming risks route matching, not just lane matching.
